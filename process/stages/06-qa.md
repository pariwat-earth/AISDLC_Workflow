# Stage 6 — QA

## Who
QA. The Risk reviewer (human) checks the risk areas. A bug → open an issue in `QA/issues.md` → back to Dev.

## How
Three rounds in order. A round starts when the one before it has passed.

### Round 1 — write cases from the requirement
- Starts as soon as tasks are broken down, in parallel with stages 4–5.
- Write to `QA/test_plan.md` from the requirement and the SA document, **without reading the code**. A case written after reading code tests what the code does, not what the user needs.
- Mark the **core cases**: the main job of each role from the BA analysis. Skills: `risk-based-testing`, then `ai-test-generation`.
- **Write the core cases first and send them to the human for approval**, each as "When …, the system must …", before Dev starts. Code and tests come from the same AI; a misunderstanding makes both wrong in the same way. The human is the one who confirms the cases match the real work.
- A requirement or SA section that turns out ambiguous → report to the human at once.

### Round 2 — test function
- Starts when stage 5 is done. Walk the real work process role by role, core cases first. Skills: `playwright-automation`, `exploratory-testing`.
- Passes when every core case passes after fixes.
- **Independent reviewer for risk areas** (money · permissions · DB migration · core cases): a subagent that has not seen Dev's conversation reviews them, given only the relevant requirement and SA sections plus the diff. A reviewer who does not know what Dev intended sees what Dev overlooked. Other areas are reviewed in the same session, because a subagent costs extra tokens.
- **Human risk review** (full level, before stage 7): PM prepares a risk-review pack in plain language — each rule, the file that enforces it, the cases that cover it, and steps to try breaking it on the test system (for example: sign in as shop A, open shop B's bill by its link). The Risk reviewer works through it and answers pass or fail per item. A reviewer who reads code also reads the cited files.

### Round 3 — test quality beyond function
- Every row of section 1 in [`process/nfr-baseline.md`](../nfr-baseline.md), plus the extra items the requirement names. Skills: `/security-review`, `accessibility-testing`.
- Run this round only after the core functions pass, because the code is still changing before that.

### Escalation
When the same issue (by issue ID) fails its fix **3 times**, or a conflict needs a decision (design against implementation, a requirement that reads two ways) → **PM stops the loop at once**. Report: what the problem is, how many attempts and by which methods, the possible options. Wait for the human's answer. Skill `diagnosing-bugs` on every issue before its third attempt.

Before opening an issue, check the accepted-risk table (CLAUDE.md section 4.2).

## Output
`QA/test_plan.md`, `QA/issues.md`

## Done when
Every requirement item has a test case · the NFR baseline table has no empty row · every issue is closed or accepted by the human as an accepted risk · the risk-review pack has an answer on every item (full level).

## Human approves
The core cases (round 1) · the risk-review pack answers · the QA report with the CI run link.
